## 3. 发现（按严重度）

### P0 — 会让“门禁”失效

#### P0-1 spec 门可被完全跳过（`dispatch` 不校验 spec_gate）

- **证据**：`cmd_dispatch`（`towerctl.py:550-566`）只检查 `status == ready`，不检查 `spec_gate`；
  只有 `check --phase ready`（`:495-503`）才看 spec 门。
- **实测**（临时塔）：未 `spec-approve` 时
  `check --phase ready` → exit 2（`spec gate not passed`），
  但 `dispatch` → exit 0（成功派发）。
- **影响**：`TOWER.md` 声称的“spec 是第一道闸”在流程上可以**一步不落地跳过**。`check` 是旁路诊断，不是前置条件。
- **修法**：`dispatch` 前置 `spec_gate == PASS`；`check` 结果写回状态并成为后续命令的硬前置。

#### P0-2 PILOT-001 自身从未走过 spec 门

- **证据**：`ledger/primary.jsonl` 18 条事件中**没有 `SPEC_APPROVED`**；
  `tasks/PILOT-001/record.json` 没有 `spec_path` / `spec_sha256` / `spec_gate` 字段；
  `pilot/PILOT-001.spec.json` 存在，但从未被绑定进任务卡。
- **影响**：首个闭环的“第一道闸”事实上没跑过；“spec 冻结”性质对 PILOT-001 不成立。
  且 `check --phase spec` 对这类旧卡直接返回“legacy task”，`check --phase ready` 又因 `spec_path` 为空而跳过检查（`:502`）——
  **旧卡 = 永久豁免**。
- **修法**：历史不补造事件（不重写）；新卡强制 `spec_path`；旧卡在审计中标记为 legacy 豁免，不得再复用。

#### P0-3 merge 不校验目标分支

- **证据**：`cmd_merge`（`:1237-1239`）直接 `git merge --no-ff <branch>`，
  未断言当前 `HEAD` 分支 == `env.base`。
- **影响**：只要工作区停在别的分支（例如 `pilot/PILOT-001`），merge 会写进**错误分支**，
  而 10 项 envelope 校验仍会全过。
- **修法**：merge 前 `git rev-parse --abbrev-ref HEAD` 必须等于 `base`，否则 `CORRECTION_REQUIRED`。

#### P0-4 handoff 生成/校验写死 pilot

- **证据**：`current_snapshot`（`:681-722`）写死 `PILOT-001`、`ENV-PILOT-001`、`pilot/repo`、`pilot/worktrees/PILOT-001`；
  `handoff-new`（`:763-916`）正文写死 §0a（“merge envelope 5 项…”）、§1（“Phase 2 已验证”）、
  §3（“Pilot repo”）、§4（“无在途任务”）、§7（`tasks/PILOT-001/…`）。
- **影响**：换任何真实项目，`handoff-new` 都会生成一份**声称自己是 Pilot-001/Phase 2** 的错误交接包；
  `handoff-check` 也会去校验错对象。**这是接第二个项目前的功能性阻断。**
- **修法**：task / envelope / repo / worktree 参数化；§4 从 `TASK_BOARD` 生成；§0a 由真实比对生成。

#### P0-5 accept / close 不校验证据，“证据门”只在可选的 check 里

- **证据**：`cmd_accept`（`:634-651`）与 `cmd_close`（`:654-678`）均不调用 `check_evidence`；
  只有 `check --phase accept/close`（`:524-535`）才算哈希，而 accept/close 不要求先跑 check。
- **影响**：`control-tower/SKILL.md` 写的“只有证据 + check 通过才能 accept/close”**不是代码事实**；
  0 份或任意 1 份证据都能收口。
- **修法**：accept/close 内联 `check_evidence` + 最低证据数 + `check` 结果写成状态字段。

#### P0-6 reviewer 空值穿透“独立性”门

- **证据**：`checkback` 只比较 `args.reviewer == rec.executor`（`:614-615`），传 `--reviewer ""` 即通过；
  `envelope_checks` 的 `reviewer != executor`（`:250-251`）对 `""` 也为真；
  `check --phase review` 仅在 reviewer 为真时比较（`:521-522`）。
- **影响**：merge 可以带着**空 reviewer** 的 PASS 通过。
- **修法**：reviewer 非空 + 格式校验；统一 ID 归一化；merge 前要求 review 记录完整（reviewer/at/verdict）。

### P1 — 治理与可复现性缺口

#### P1-1 `allowed_paths` 只存不验

- **证据**：全文 grep，`allowed_paths` 只出现在 spec 校验（`:382-384`）、必填检查（`:397`）、
  写入 record（`:416`）、打印到 TASK.md（`:432`）；没有任何 `git diff --name-only` 校验。
- **影响**：“executor 只在 allowed_paths 内写”目前**只靠 reviewer 人眼**（PILOT-001 的 review note 里就是手写 “git scope clean”）。
- **修法**：`check --phase deliver` 增加 `git diff --name-only base..head ⊆ allowed_paths`。

#### P1-2 ledger 无哈希链、无锁、坏行静默跳过

- **证据**：`append_ledger`（`:66-80`）只取 `max(seq)`，解析失败 `except: continue`；
  事件结构只有 `seq/at/type/actor/payload`，无 `hash` / `prev_hash`；两个进程并发 append 无文件锁。
- **影响**：事后删行/改行**不可检测**；并发写可能丢事件或产生重复 seq。
- **讽刺点**：PILOT-001 交付的正是“SHA-256 哈希链 + 篡改检测”，但**塔自己的 ledger 没有用它**。
- **修法**：dogfood `ledger_chain.py`，给 `ledger/*.jsonl` 加 `prev_hash/hash`；写入前加 `.lock`。

#### P1-3 证据哈希语义未定义 + CRLF 陷阱

- **证据**：同一个 `ledger_chain.py` 出现三种哈希：
  evidence 副本 `38ced80e…`（= git blob，LF）、
  当前 worktree 文件 `bd9444…`（CRLF）、
  git blob `38ced80e…`。
  `core.autocrlf=true`，仓库无 `.gitattributes`。
- **影响**：复核者在 worktree 里重算会**误报证据不符**；`deliver` 从 CRLF 工作区取件会产出与 git blob 不一致的证据。
- **修法**：明确“证据以 git blob（LF）为准”；加 `.gitattributes`（`* text=auto eol=lf`）；
  `check` 时用 `git cat-file blob` 对比，而不是只比副本。

#### P1-4 closeout 文案写死

- **证据**：`cmd_close`（`:654-678`）硬编码 `"Merge: **not performed** (first version; …)"`；
  PILOT-001 的 `CLOSEOUT.md` 因此在 Phase 2 合并后**自相矛盾**。
- **修法**：closeout 只描述 close 时刻；merge 结果由 `post-merge` 追加独立文件（本次已用“补记”方式止血）。

#### P1-5 相位漂移（文档层）

- **证据**：`TOWER.md` / `README.md` 写 Phase 2；`shared/PROJECT_PROFILE.json` 仍 `PHASE_2_DUAL_TOWER`；
  `~/.agents/skills/control-tower/SKILL.md` 仍写“Phase 1 不启用 v2.1 交接”。
- **状态**：TOWER / README 已修（本次）；PROJECT_PROFILE 与 skill 留待 owner 决定。

#### P1-6 控制面自身无版本控制、无备份

- **证据**：`tower-dsh` **不是 git 仓库**（`git rev-parse` → not a git repository）；
  唯一真相源（ledger + 状态）没有历史、没有远端、没有备份。

#### P1-7 `towerctl` 无测试

- **证据**：仓库无 `test_*.py` 针对 `towerctl.py`；32 个子命令 0 个回归测试。
- **影响**：门禁逻辑只能靠“读过代码”保证；任何改动都是裸奔。

#### P1-8 `correction_return` 只有声明没有实现

- **证据**：`shared/AUTHORITY_MODEL.json` 把 `correction_return` 列为监督塔职责；
  `supervision/outbox/corrections/` 目录存在但为空；`towerctl` 无任何 correction 子命令。
- **影响**：`CORRECTION_REQUIRED` 只是一个状态值，没有纠正单、没有回退路径。

#### P1-9 空测试集也能 post-merge PASS

- **证据**：`cmd_post_merge`（`:1280-1294`）以 `unittest discover` 的退出码为唯一标准；
  项目若没有 `tests/`，discover 返回 0 → “post-merge tests pass”。
- **修法**：要求 `Ran N tests` 且 N > 0。

## 附录 A — 最小绕过链（静态推演，未在本塔执行）

```text
task-new → dispatch → deliver（任意 1 个文件）
  → checkback --reviewer "" → accept → envelope-new → queue-add → merge
```

全程：无 `SPEC_APPROVED`、无 `check`、无 6 项证据、reviewer 为空。
每一步都能在代码里找到“只认可手改的状态字段、不认前置检查”的入口。

**结论**：`towerctl` 的 30 个子命令里，真正被后续命令引用的前置条件只有
